# ADR 0003: операции над проектом и синхронизация

Статус: принято
Дата: 2026-09-19

Основание: совместная работа над проектом без сети и с несколькими редакторами.

## Решения

| Вопрос | Решение |
|---|---|
| Совместная работа | несколько редакторов одновременно и долгая работа без сети |
| Роли | `owner`, `editor`, `viewer` на проект |
| Модель данных | таблицы сущностей остаются; изменения идут операциями |
| Операции | `insert`, `set`, `delete`, `move` над коллекциями из `contracts/ops/project.schema.json` |
| Интерпретатор | `api/internal/ops` (эталон) и `web/src/store/apply.ts`; фикстуры создает Go, TS получает тот же результат |
| Клиент | кэш в памяти и IndexedDB, очередь транзакций, оптимистичное применение |
| Уведомления | SSE от сервера, POST от клиента, LISTEN/NOTIFY между экземплярами API |
| История | undo и redo только в сеансе, обратными транзакциями |
| Конфликт после офлайна | транзакция не применяется и попадает в список "Не применено" |
| Расчеты | только Go на сервере, это не операции |
| Главный источник | сервер |

Не вводим: CRDT, WebSocket, Redis, Kafka, `apply()` через WASM, отдельный код каждой операции на двух языках.

## Словарь схемы

Словарь фиксирован. Новое слово только через новый ADR. Требование, которое словарем не выражается, становится проверкой на Go перед расчетом или макросом в TS.

- Коллекция: `kind` (`singleton` или `list`), `ordered`, `max_items`, `unique`, `fields`, `requires`.
- Типы полей: `string`, `int`, `number`, `bool`, `enum`, `point`, `points`, `object`, `params`, `ref`, `ref_list`, `external_ref`.
- Ограничения: `min`, `max` (числа), `min_length`, `max_length` (символы строки, элементы `points` и `ref_list`), `nullable`, `required`, `immutable`, `values` (`enum`), `validator` (имя проверки для `object`).
- Ссылки: `to`, `key` (по умолчанию `id`; иначе неизменяемое уникальное строковое поле цели), `on_delete`: `cascade` и `set_null` для `ref`, `remove` для `ref_list`.
- `requires`: `{"if_set": "a", "then_nonempty": "b"}`. Задано: не `null`. Непусто: не `null`, строка не из одних пробелов, непустой список.

## Смысл примитивов

- Запись: `id`, `order` у упорядоченной коллекции, затем все поля схемы.
- Singleton: одна запись с `id`, равным имени коллекции. Существует всегда, `insert` и `delete` отклоняются с `immutable`. В `set` `id` можно не указывать.
- `insert`: `id` от клиента, UUID в нижнем регистре. Коллекции карты (`legacy_ids`) принимают и id вида `p1` (1-64 символа: латиница, цифры, `-`, `_`, `.`): такие id были у карт до операций, и отмена удаления возвращает запись под прежним id. Новые записи клиент создает только с UUID. Не указанное поле получает `null`, если поле `nullable`, иначе нулевое значение типа (`""`, `0`, `false`, `[]`, `{}` для `params`, `{x: 0, y: 0}` для `point`). Поле с `required` указать обязательно. `id` в значении и неизвестные поля отклоняются.
- `set`: новое значение поля или `поле.ключ` для `object` и `params`. Путь глубже одного ключа отклоняется. Равное текущему значение ничего не меняет, транзакция применяется.
- `delete`: удаляет запись и выполняет `on_delete` у всех ссылок на нее, рекурсивно.
- `move`: новый ключ порядка упорядоченной записи.
- Ключ порядка: дробная индексация, алгоритм npm `fractional-indexing` (`api/internal/ops/order.go`, `web/src/store/order.ts`). Порядок записей: ключ, затем `id`. `sort_order` в таблицах и черновике равен позиции записи.

## Проверки

Порядок проверок одинаков на Go и TS, фикстуры его закрепляют.

1. На каждой операции: вид операции и коллекция, существование цели (`target_missing`), путь, тип и ограничения значения, `immutable`, именованный валидатор `object`.
2. После всех операций, по записям в порядке первого изменения: ссылки (`ref_missing`), `external_ref` через хук, `params` через хук, `requires`. Проверяются только поля, заданные операциями: каскад не проверяет старые ссылки записи.
3. Затем по коллекциям, где были `insert` или `set`: `max_items` (`limit`, только при вставке), `unique` (только для записей, у которых менялось поле набора). `null` в `unique` равен `null`.

Любое нарушение отклоняет всю транзакцию. Результат отказа: причина и `{op, coll, id, field}`.

## Изменения (Changes)

Применение возвращает чистый итог по каждой затронутой записи в порядке первого касания: `insert` с `after`, `delete` с `before`, `update` с `before` и `after`. Каскад входит в итог. Из него строится обратная транзакция undo.

## Хуки

- `params`: поле типа `params` проверяется схемой типа объекта записи (`object_type`, `api/internal/objects`). Проверяются заданные ключи, при замене всего поля все ключи. Смена `object_type` проверяет все поля `params` записи целиком: параметры прежнего типа не проходят, их заменяют в той же транзакции.
- `object`: именованные валидаторы (`process_demand`, `process_sla`, `process_durations`, `process_staff`, `financing_assumptions`, `econ_overrides`, `solution_ids`, `map_page`, `map_segment`).
- Объекты, которые таблицы хранят через структуру Go (`process_demand`, `process_sla`, `process_durations`, `process_staff`, `map_page`, `map_segment`), сервер принимает только в хранимой форме: ключ с нулевым значением у поля с `omitempty` отсутствует, остальные ключи есть всегда. Иначе следующий снимок отличался бы от состояния клиента. Обнулить такой ключ можно только заменой всего объекта.
- `external_ref`: решение каталога в закрепленной ревизии проекта.
- Клиент, который не может проверить значение, пропускает его, решает сервер.
- Фикстуры используют заглушки из `contracts/ops/fixtures/hooks.json`: `params` по таблице типа объекта; `object` проверяет разрешенные ключи (`number` не меньше 0, `string`, `any`) или список строк; `external_ref` по списку id.

## Проект в коллекциях

- `project`: имя, тип объекта, параметры, выбор подбора, переопределения экономики, активный набор допущений (`active_assumption_set_id` вместо флага `is_active` у набора).
- `processes`, `variants`, `fleet_items`, `financing`, `shared_costs`, `assumption_sets`: строки таблиц с теми же id.
- `map` (singleton): страница, профиль, масштаб, отрезки калибровки и проверки. Карта есть, если `map.page` не `null`.
- `map_points` (координата `pos` одним значением, чтобы два перемещения не смешали x и y), `map_edges`, `map_zones`, `map_obstacles` (упорядочены: порядок отрисовки), `map_resources`, `map_flows`. Поток получил постоянный `id` в документе карты; у старых карт он выводится из кода процесса.
- `ops.FromDraft` и `ops.ToDraft` переводят черновик в коллекции и обратно. Сообщения проверки карты (`errors`, `warnings`) пишет сервер при сохранении.

## Сервер

Решения реализации:

- `POST /api/projects/{id}/transactions` работает под блокировкой строки проекта: пачки в один проект идут по очереди, `seq` растет без пропусков. Состояние собирается из таблиц (`ops.FromDraft`), после пачки таблицы затронутых коллекций переписываются целиком с id и ключами порядка записей, затем черновик и `input_hash` пересчитываются. Сообщения проверки карты пересчитываются, только если менялась карта. Смена `object_type` отцепляет текущий запуск и результат: запуск остается в истории, но отвечает на вопрос о другом объекте.
- Повтор `tx_id` возвращает сохраненный исход. Неразборчивая операция отклоняет свою транзакцию с `invalid_value`, а не всю пачку: иначе одна плохая запись остановила бы очередь клиента.
- Числа в таблицах без масштаба (`NUMERIC`), чтобы значение из операции сохранялось точно.
- Журнал `project_operations` хранит и отклоненные транзакции (без `seq`, с причиной). Записи сервера имеют `client_id = "server"`: расчет и подбор меняют выбор решений и переопределения через `set` с меткой `calculate` или `match`, только если значение изменилось. Расчет пишет `calculation_runs.draft_seq`; если черновик изменился за время расчета, черновик не трогается и новый запуск сразу устаревший.
- PUT содержимого проекта больше нет: все правки идут транзакциями. `reset` в журнале остался один: копия проекта (`logReset(ctx, id, "copy")`), которая заполняет новый проект мимо операций; клиенты, дойдя до такой записи, берут снимок.
- Проект получает процессы, варианты и наборы допущений по умолчанию, только пока `draft_seq = 0`. После первой правки пустой список это выбор пользователей.
- `POST /api/projects/import` создает проект из снимка браузера: `ops.Rekey` выдает записям новые идентификаторы (старые принадлежат тому проекту, откуда снимок), `ops.Replace` превращает разницу между заготовкой нового проекта и снимком в одну транзакцию, и она проходит те же проверки схемы, что обычная правка. Создание и заполнение идут в одной транзакции базы: снимок, который схема не приняла, не оставляет ни проекта, ни записей.
- `GET /snapshot` отдает `{schema_version, seq, collections}`, `GET /operations?after=` принятые транзакции по порядку или `reset: true` (в диапазоне `reset`, часть журнала старше 30 дней или `after` больше `seq`).
- SSE `GET /events`: пакет `api/internal/realtime`, одно соединение `LISTEN` на процесс вне пула. `runs`, `access` и `deleted` шлют триггеры Postgres (миграция 0014), поэтому их видят все экземпляры API и все пути записи, включая воркеры. После потери соединения `LISTEN` каждый поток получает `reset`. Маршрут вне таймаута запроса, сессия проверяется на каждом heartbeat.
- Присутствие: `POST /presence` рассылается через `NOTIFY`, каждый процесс держит список в памяти. Запись ключуется `user_id/client_id`, так что чужой `client_id` не затрагивает запись другого человека, и живет 90 с (фоновая вкладка получает таймер раз в минуту).

## Клиент

- `web/src/store/`: хранилище проекта (`confirmed` и очередь `pending`, вид со структурным разделением), синхронизация с паузой от 1 до 60 с, IndexedDB `robots-store`, один поток SSE на браузер через Web Lock и `BroadcastChannel`. Идентификатор вкладки (`clientId`, ключ очереди) лежит в `sessionStorage` только пока страница ушла (`pagehide`, `freeze`): перезагрузка находит его и сохраняет очередь, а «Дублировать вкладку» копирует хранилище живой страницы, где его нет, и получает свой. Список «Не применено» хранится по тому же ключу проект, человек, вкладка; очередь и список закрывшейся вкладки забирает соседняя вкладка того же человека. Хранилище и поток живут, пока открыта любая страница проекта: их держит статус сохранения в верхней панели.
- Карта (`web/src/map/records.ts`): документ строится из записей так же, как `toMap` на сервере (совпадение проверяет `contracts/ops/map_document.json`). Команда редактора превращается в операции одной транзакции; удаление точки дает одну операцию, остальное удаляет каскад схемы. Перетаскивание рисуется локально, транзакция уходит при отпускании мыши. Координаты округляются до 0,01 пикселя, как при старом сохранении. Шаблон и загруженный документ заменяют карту одной транзакцией и сохраняют свои id.
- Новые объекты карты получают UUID и название-код (`T4`, `e2`, `z3`, `res-1`), пронумерованное как id до операций. Объекты старых карт показывают свой id. Сообщения проверки карты называют объекты так же; ребро с UUID называется по концам.
- Undo и redo (`web/src/store/undo.ts`): стек на вкладку и проект, только свои транзакции. Шаг хранит изменения своей транзакции, отмена отправляет обратную транзакцию против текущего состояния, поэтому чужие правки других полей остаются. Запись, которую шаг вставил, а другой уже удалил, не трогается; изменение записи, которую другой удалил, не применяется и попадает в "Не применено". Сдвиги стрелками одной точки подряд образуют один шаг. Так же, как в Figma, отмена возвращает значение своей вкладки поверх более новой чужой правки того же поля, а повтор возвращает чужое: обратная транзакция всегда пишет значение, которое было в момент шага.
- Варианты (`web/src/fleet/records.ts`): правка одного поля дает одну транзакцию с понятной меткой ("Добавить робота", "Убрать робота"). Порядок флота хранится ключами порядка: запись, оставшаяся на своем месте, ключ не меняет, вернувшаяся на прежнее место получает ключ между соседями. Копия варианта вставляет вариант, флот и финансирование с новыми id. Удаление варианта это одна операция, флот и финансирование удаляет каскад.
- Поле формы сохраняется через 600 мс после ввода, по Enter и при выходе из поля (D1), общий хук `web/src/ui/fieldDraft.ts`. Значение, которое схема не примет (пустое имя), остается у поля и не отправляется. Диапазоны параметров объекта схема операций оставляет серверу, поэтому форма проверяет их сама (`web/src/params/check.ts`) перед записью: иначе значение вне диапазона применилось бы на месте и вернулось отказом позже.
- Гость (`web/src/store/guestSync.ts`): проект `guest` живет в том же хранилище, но за ним нет сервера, поэтому каждая принятая транзакция подтверждается на месте и состояние сразу пишется в IndexedDB. Строка в верхней панели ("Сохранено в браузере") следует за записью, а не за правкой: закрыть вкладку безопасно ровно тогда, когда она это говорит. Первый снимок собирается из умолчаний схемы типа и ключей `guest-*` прежних версий, после чего ключи удаляются. Другие вкладки того же демо получают каждую транзакцию через `BroadcastChannel` `robots-demo-<тип>` и применяют её как свою следующую; то, что уже не применяется (запись удалена здесь), пропускается.
- Расчёт демо: `POST /api/guest/calculate` и `/api/guest/export` принимают `schema_version` и `collections`, проверяют их как импорт проекта и считают по черновику из них (процессы, варианты с флотом, финансирование, допущения, общие расходы, что-если). Ничего не сохраняется. Браузерное `calculate` принимает те же `collections`. Ключ результата демо включает отпечаток записей (`web/src/store/fingerprint.ts`), поэтому правка процесса, флота или допущения пересчитывается. Демо склада сеется из `demo-warehouse.json`; его `version` (хеш записей) хранится вместе со снимком в IndexedDB, и демо со старой версией сеется заново: сервера у демо нет, мигрировать нечего.
- Браузерное ядро (`web/src/engine/`): страница просит сервер и переходит на движок в браузере, только когда запрос до сервера не дошел; такой результат помечен "Предварительно", не сохраняется и не дает выгрузить отчет. Сборка `VITE_APP_MODE=demo` сервера не имеет вовсе и считает всегда в браузере, поэтому отметку не показывает.
- Отказ сервера (`web/src/store/rejected.ts`, `web/src/layout/RejectedList.tsx`): транзакция, которую сервер не принял, остается записью с названием действия, причиной по-русски и временем. "Восстановить" пишет ту же правку заново против текущего состояния: запись, которой уже нет, вставляется с прежними значениями, существующая получает поля, которые правка меняла. В момент отказа выходит toast. Если запись удалил другой участник, строка называет его почту (`actor_email` в `/operations`), а свои удаления из другой вкладки помечает «удалено в другой вкладке».
- Присутствие (`web/src/store/presence.ts`): страница сообщает о себе на `POST /api/projects/{id}/presence` при смене места и раз в 15 с, при возврате из кэша или из фона сообщает снова, а при закрытии прощается с `keepalive`. Идентификатор присутствия новый на каждую загрузку (`pageId()`, не общий с очередью правок), поэтому прощание старой страницы не стирает запись перезагруженной. Место (`Layout`) и выделение (`useReportSelection`, при уходе со страницы сбрасывается) сообщаются отдельно, на любой странице проекта. Сервер шлет список событием `presence` (`{"list": [...]}`). Свои же вкладки (тот же `user_id`) в лица не попадают, вкладки другого человека сводятся в одно лицо. В демо присутствия нет. Цвет закреплен за человеком хешем его id, четыре токена `--presence-1..4` на тему.
