# ADR 0001: снимки, варианты, jobs и событийное ядро

Статус: принято
Дата: 2026-09-16

## Контекст

Текущая модель хранит изменяемые `projects.params` и перезаписывает `projects.results`. Изменение входа не помечает результат устаревшим. Один робот и три финансовых kind живут в одном JSON. Симуляция синхронна и не сохраняет журнал.

Кандидат к 2026-09-29 показывает один складской сценарий. Полный пилот после сдачи.

## Решение

### Снимки

- Черновик проекта изменяемый. Канонический документ: `ProjectDraft`.
- Расчет создает неизменяемые `project_versions` (`ProjectSnapshot`) и `calculation_runs`.
- Сервер считает `input_hash` = SHA-256 канонического JSON. В hash входят params, процессы, варианты, флот, финансирование, карта, ревизия каталога, выбранные id, econ overrides, версии match/econ/sim.
- Порядок ключей и неупорядоченных массивов нормализуется сервером. `sort_order` процессов и вариантов сохраняется. Params хешируются так, как их читает схема (`objects.NormalizeParams`): миграция, которая меняет только формат хранения, hash не меняет.
- Seed запуска в hash не входит. Seed хранится на запуске.
- Если hash черновика не равен hash текущего запуска: результат `stale`, экспорт текущего результата блокируется, исторический запуск открывается явно.
- С запуском сравнивается `calculation_runs.draft_hash`: снимок запуска, посчитанный текущим определением hash. `input_hash` запуска остается тем, что записан при расчете, и идет в отчеты. Смена определения hash сама по себе не делает запуск устаревшим: миграция обнуляет `draft_hash`, API пересчитывает его из снимка при следующем сохранении черновика. Запуск другой версии econ или match остается устаревшим. Тест `TestInputHashGolden` падает при любой смене hash.
- `projects.results` остается кэшем последнего запуска. Источник истины: `calculation_runs` + `calculation_results`.

### Варианты

- Процессы принадлежат проекту и образуют общую базу.
- `solution_variants` задают технический состав. `variant_fleet_items` допускают смешанный флот.
- `financing_scenarios` отделены от флота. Один вариант сравнивает buy и тарифы RaaS без копирования состава.
- Одновременно до шести вариантов, по умолчанию три черновика.
- Не использовать таблицу `scenarios` из 0001. Она не часть этой модели.

### Jobs

- Длинная симуляция идет через `simulation_jobs` и встроенный worker pool в том же API-процессе.
- HTTP не ждет прогон. Клиент читает статус по `job_id`.
- Отмена, повтор и квота по пользователю или проекту. Без Redis и отдельных воркеров.
- Реализация очереди: 22-24 сентября. Контракт фиксируется сейчас.

### Событийное ядро

- `sim-v1` остается геометрическим прогоном до замены.
- `sim-v2` (22-24 сентября) пишет компактный журнал `SimulationEvent`.
- Сервер отдает события и контрольные состояния, не покадровый снимок сцены.
- Типы событий склада: `job_arrival`, `dispatch`, `route_start`, `route_end`, `resource_acquire`, `resource_release`, `load`, `unload`, `charge_start`, `charge_end`, `sla_reached`, `sla_violated`.
- Профили AMR и паллетного класса не сводятся к одним коэффициентам.

### Карта

- Черновик: `MapDocument` в JSONB. Исходный PNG/JPEG/PDF на сервер не пишется.
- Снимок карты входит в `ProjectSnapshot` и неизменяем.
- Профиль склада: `indoor`.

## Последствия

- Backend и frontend реализуют один контракт из `api/openapi.yaml` и `contracts/jsonschema/`.
- Миграции только forward-only.
- Нельзя убирать hash, stale, неизменяемый запуск и серверную валидацию.
