# Сопровождение

Раздел описывает то, что нужно сделать перед публикацией платформы, и то, что может сломать стенд или данные. Команды первого запуска приведены в разделе [Развёртывание](guide/02-install.md), полный список переменных окружения в разделе [Переменные окружения](reference/env.md).

## Перед публикацией в сети

1. Смените демонстрационные пароли (`DEMO_USER_PASSWORD`, `DEMO_ADMIN_PASSWORD`).
2. Настройте HTTPS на внешнем прокси. В составе `docker-compose.yml` шифрование не включено.
3. Задайте `COOKIE_SECURE=true`.
4. Задайте `PUBLIC_ORIGIN` равным адресу сайта, с тем же протоколом и портом, с которыми открывается интерфейс. Если значение не совпадает с адресом страницы, изменяющие запросы отклоняются с ошибкой `csrf`.
5. Не оставляйте `APP_ENV=local`. При этом значении открыт просмотр писем `GET /api/dev/outbox`.
6. Выберите режим регистрации: `REGISTRATION_MODE=invite` разрешает регистрацию только по приглашению.
7. Решите, как отправлять письма. По умолчанию (`MAIL_MODE=capture`) письма остаются в базе и наружу не уходят. Чтобы отправлять их, задайте `MAIL_MODE=smtp` и параметры `SMTP_HOST`, `SMTP_PORT`, `SMTP_USER`, `SMTP_PASSWORD`.

## Запуск и сброс

Запуск:

```bash
docker compose up --build
```

Интерфейс открывается по адресу http://localhost, проверка API по адресу http://localhost:8080/health. Миграции применяются при старте API.

Сброс удаляет том базы. Пропадают проекты, запуски и учётные записи:

```bash
docker compose down -v
```

Следующий запуск заново загрузит каталог из CSV, потому что таблица пуста, и создаст демонстрационные учётные записи. На стенде, данные которого нужно сохранить, `-v` не указывайте.

## Резервная копия базы

Перед миграцией снимите копию. В локальном Compose сервис называется `db`, пользователь и база `app`. На стенде подставьте свои значения.

```bash
docker compose exec db pg_dump -U app app > backup.sql
```

Восстановление стирает текущую базу и записывает копию на её место. Не запускайте его, если файл копии не открывается. Команды ниже написаны для локального Compose.

```bash
docker compose stop api
docker compose exec db dropdb -U app --force --if-exists app
docker compose exec db createdb -U app app
docker compose exec -T db psql -U app -d app < backup.sql
docker compose up -d
```

Копию со схемой старше текущего кода API догонят миграции при старте, если в применённые файлы не вносились ручные правки. Если `psql` останавливается на ошибке, не запускайте ту же команду повторно: сохраните текст ошибки и передайте разработчику.

## Миграции

Файлы лежат в каталоге `api/migrations`. Применённый файл не правят. Новое изменение схемы записывают новым файлом. Парный файл `down` нужен, чтобы миграция была обратимой по замыслу. На стенде с данными `down` не запускают.

## Хранение данных

| Данные | Срок по умолчанию | Переменная |
|---|---|---|
| Удалённый проект в корзине | 30 дней | `TRASH_RETENTION_DAYS` |
| Журнал событий симуляции | 90 дней (закреплённый не удаляется) | `SIM_LOG_RETENTION_DAYS` |
| Сессия без запросов | 168 часов | `SESSION_IDLE_HOURS` |
| Предельный срок сессии | 30 дней | `SESSION_MAX_DAYS` |
| Журнал действий администратора | 365 дней | нет |

Окончательное удаление проекта удаляет и связанные с ним данные.

## Если стенд не отвечает

1. Откройте http://localhost:8080/health. Ответ 200 значит, что процесс API работает.
2. Посмотрите журнал API:

   ```bash
   docker compose logs api
   ```

   В строках журнала есть `request_id`, при действиях с проектом также `project_id` и `op`. Пароли и токены в журнал не попадают.
3. Если веб-сервер отвечает, а API нет, интерфейс показывает сообщение «Сервер не отвечает. Повторите через минуту.» (код `api_unavailable`).
4. Если контейнеры остановились после перезапуска Docker, пересоздайте сеть Compose без удаления данных:

   ```bash
   docker compose down && docker compose up -d
   ```

Если просите помощи, передайте `request_id` из ошибки, а не снимок экрана с паролями.
