# Запуск и сопровождение

Команды первого запуска, локальный запуск без Docker и полная таблица переменных в [README репозитория](../README.md). Здесь только то, что ломает стенд или данные.

## Перед внешней выкладкой

Смените демо-пароли. Адреса и текущие пароли написаны в README репозитория.

Снаружи сайт должен открываться по HTTPS. Задайте `COOKIE_SECURE=true` и `PUBLIC_ORIGIN` равным адресу сайта, с тем же протоколом и портом, с которыми открыт интерфейс. Если `PUBLIC_ORIGIN` не совпадает с адресом страницы, изменяющие запросы отклоняются.

Письма по умолчанию остаются в базе и наружу не уходят. Регистрация по приглашениям включается так: `REGISTRATION_MODE=invite`. Остальные имена, включая SMTP, в таблице переменных README. На выкладке не оставляйте `APP_ENV=local`: в этом значении доступен просмотр писем.

## Запуск и сброс

```bash
docker compose up --build
```

Интерфейс: http://localhost. Проверка API: http://localhost:8080/health. Миграции применяются при старте API.

Эта команда удаляет том базы. Пропадают проекты, запуски и аккаунты.

```bash
docker compose down -v
```

Следующий `docker compose up` заново загрузит каталог из CSV, потому что таблица пустая, и создаст демо-аккаунты. На стенде, который надо сохранить, `-v` не ставьте.

## Копия базы

Перед миграцией снимите дамп. В локальном compose сервис называется `db`, пользователь и база `app`. На выкладке подставьте своего пользователя и имя базы, не эти значения.

```bash
docker compose exec db pg_dump -U app app > backup.sql
```

Восстановление стирает текущую базу и кладёт дамп на её место. Не запускайте его, если файл дампа не открывается. Команды ниже для локального compose, пользователь `app`.

```bash
docker compose stop api
docker compose exec db dropdb -U app --force --if-exists app
docker compose exec db createdb -U app app
docker compose exec -T db psql -U app -d app < backup.sql
docker compose up -d
```

Дамп со схемы старше текущего кода API догонит миграциями при старте, если между ними нет ручных правок применённых файлов. Если `psql` останавливается на ошибке, стенд не чините повторным запуском той же команды: пришлите текст ошибки разработчику.

## Миграции

Файлы лежат в `api/migrations`. Применённый файл не правят. Новое изменение схемы пишут новым файлом. Парный down-файл нужен, чтобы миграция была обратима по замыслу. На стенде с данными down не гоняют, чтобы переписать уже накатанное.

## Если стенд не отвечает

Откройте http://localhost:8080/health. Ответ 200 значит, что процесс API жив. Дальше смотрите лог API: в строке есть `request_id`, при действии с проектом ещё `project_id` и `op`. В лог не попадают пароли и токены. Если просите помощь, пришлите `request_id`, не скрин с паролем.
